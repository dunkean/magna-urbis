# Revue ciblée — une translation rigide du snapshot natif

2026-10-23. Lecture seule du code et des JSON ; aucun Cargo/natif/serveur exécuté, aucun produit modifié. **Le noyau existant convient à une correction analytique unique, sous droits réellement convexes ; il ne permet pas de conclure que les trois cas sont récupérables.** Son API s'appelle [`rigid_translation_fit::solve(TranslationProblem)`](../rust/crates/houses/src/rigid_translation_fit.rs:215), pas `closest_translation`.

Le [pilote gelé](../web/out/native-snapshot-isolated-proof/summary.json) compte trois snapshots conformes au programme, six admissions refusées à la première garde et zéro gain. Les trois sources sont Strip, deux ou trois étages. [`native_single_fit`](../rust/crates/houses/src/native_single_fit.rs:89) ne convient pas : il exige Single/un étage, redimensionne et appelle `build_layout`. Ne pas le faire entrer artificiellement dans ce chemin. Le pont à reprendre est plutôt le [probe de translation native](../rust/crates/houses/src/native_translation_probe_tests.rs:105), qui utilise une géométrie déjà résolue et une seule préparation.

**Précondition décisive déjà visible :** dans la [fixture inchangée](../web/out/houses-native-snapshot-workspace/rust/crates/houses/tests/fixtures/feasibility-recovery-f6.json), a71f31f2438f58c9 et a7aa26a199e8dc6f ont des droits bruts `buildable/cadastral/roof_domain` concaves (26/23 sommets, aucun trou ni réserve). Une vérification des demi-plans sur ces coordonnées donne respectivement environ 36,55 et 14,68 m de violation de convexité ; ce ne sont pas des quasi-alignements numériques. Les droits de toiture ordinaires ne retranchent pas les voisins : le noyau actuel doit donc les déclarer **Unsupported**, sans hull. Pour 513465e42378834d, les droits bruts à sept sommets sont convexes ; il faut encore vérifier les domaines exacts après réserves/occupation/voisins. L'export géométrique exact de l'auteur reste attendu au moment de cette note.

Suggestion précise pour un prochain test isolé :

1. Garder le snapshot sélectionné, sa configuration, dimensions, étages, variante, richesse et seed. Fixer **avant le solve** une seule pose/orientation/front existante selon l'ordre déterministe déjà retenu, par exemple la première pose native-contact. Ne pas résoudre sur chaque orientation puis choisir un résultat favorable.
2. Dans un même repère, fournir trois couples exacts : `body_local` transformé → `buildable − reserves − neighbours` ; **occupation complète** (`plan_local`, cours/chemins/features et toutes les `physical.occupation_parts`, passages d'entrée/supports compris) → `cadastral − reserves − neighbours` ; tous les toits/eaves et domaines de couverture des features → `roof_domain.unwrap_or(cadastral) − reserves`. Les voisins incluent exactement l'occupation locale du pilote. Ne pas inventer une interdiction de toiture au-dessus des voisins si le contrat ordinaire ne l'impose pas.
3. Appeler `solve` **une seule fois**. Chaque domaine de droits final doit être un unique polygone valide convexe sans trou ; limites existantes : 64 sommets par droit, 4096 sommets mobiles combinés, 256 polygones mobiles par couple. Les composants mobiles peuvent se chevaucher et être non convexes ; ils doivent tous être présents. Aucun hull, fermeture de trou, sélection d'un composant favorable ou nouveau rectangle englobant substitué au droit réel.
4. Sur `Fit`, ajouter uniquement `delta.x/delta.y` à l'origine de la pose. Garder strictement orientation et géométrie locale ; ne pas snapper ensuite le résultat vers l'extérieur. Réutiliser le même `PreparedPlan`/cache natif et appeler une seule admission ordinaire sur cette pose corrigée. Compter cette admission dans le budget total de quatre, sans augmenter les plafonds. `EmptyFixedDomains` ou `Unsupported` termine ce chemin sans autre source/pose/angle.

Le solve calcule la projection euclidienne minimale de zéro sur les contraintes exactes ; il peut donc corriger un décalage dû à une pose ancrée sur les bounds d'un domaine oblique, sans balayer une grille. Il n'impose aucun rayon arbitraire : une translation éloignée reste soumise aux mêmes accès et terrain. Une première garde générique ne prouve pas encore quelle surface/droit était violé ; exporter les trois différences séparées est nécessaire.

**Contrôles toujours pendants :** assise physique, pente/eau et supports ; entrée native et raccordement réel au même segment si cette contrainte est retenue ; toiture native détaillée et droits ; toutes les gardes ordinaires d'occupation. Réadmettre avec le front choisi (`Some(front)`) si le pilote exige ce front, plutôt que perdre cette contrainte avec `None`. Ne pas transporter un ancien connecteur externe comme s'il était déjà certifié : le raccordement doit être recalculé à la nouvelle position.

Les [`prepared.roofs()` + couvertures de features](../rust/crates/houses/src/native_translation_probe_tests.rs:85) représentent l'enveloppe cartographique ordinaire. Elles ne prouvent pas à elles seules le domaine d'une toiture native détaillée ; utiliser ses surfaces réelles si disponibles, sinon conserver explicitement `NativeRoofRealization` pending et vérifier la réalisation après admission. Les [tests existants](../rust/crates/houses/src/rigid_translation_fit_tests.rs:51) couvrent petit retrait de passage, contrainte oblique, droits toiture distincts, contacts segment/point, domaine vide et rejet concavités/trous. Ils ne démontrent aucun gain sur ces trois snapshots. Une translation vide n'est une impossibilité que pour cette géométrie/orientation et ces droits fixes.

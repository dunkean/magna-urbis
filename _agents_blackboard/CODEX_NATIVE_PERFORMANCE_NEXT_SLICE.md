# Performance native : supprimer les unions inutiles avant de changer le modèle

Sur le vrai corpus8395requêtes/132lots, les timers **natifs déjà archivés** localisent un coût important : V2 cumule152,809s dans les deux unions d’occupation des6482 tentatives de paire, pour221,828s de tempsAPI (68,9%). V1 diagnostic donne135,793/199,050s (68,2%). Ce sont des sous-intervalles **wall**, pas un profilCPU ; la machine partageait Core/TSC. Les81,144s de V2 associés à3478 refus antérieurs au premier usage du voisinage sont une opportunité observée, pas une prédiction de gainCPU. Le résiduel69,019s inclut phase1, préparation/admission, index, archives et codec : les données actuelles ne le répartissent pas. Evidence détaillée : `web/out/houses-native-performance-audit-v1/attempt-timer-analysis.json` (264 réponses natives SHA-pinnées).

La cause est directement lisible dans `native_assembly_builder.rs:63–81` : validation complète, puis `unite(land)`/`unite(roof)`, puis seulement les gates de `build:103–173`. Après avoir payé les unions,2597 tentatives refusent l’absence de corps/portail/niveau compatible,590 ont déjà assez de brut,105 un descripteur non supporté,98 aucun créneau dimensionnel,65 aucun accès déclaré correspondant,23 sont hors scope. V2 transmet1,378,457 slots de parties land et348,491 roof, **avec les vides et répétitions**, pas autant de géométries uniques. `native_parent_batch.rs:224–226` reconstruit ces listes pour chaque parent parmi au plus64 : coûtO(N·B), B≤64, pas un clone des graphes de toute la ville.

La tranche suivante est implémentée séparément dans `houses-native-lazy-occupation-union-workspace-v1` : **un fichier runtime**, produit frais/growthOLD. Garder `resource_preflight`, `validate_request`, toute validation de chaque partie et l’ordre intégral des gates ; déplacer seulement les deux unions après la recherche de l’accès retenu, juste avant `external`. Même ordre de parties, mêmes booléens/source/dimensions/RNG/budgets et fallback entier ; aucune exclusion de voisin, soustraction d’incumbent à une union globale, approximationBBox ou nouveau cache. `occupation_union_ms=None` indique désormais aussi une union non exécutée ; le compteur cfg(test) distingue0/2 appels. Lot2 éventuel : éviter les clones en empruntant les feuilles, **après mesure** et preuve d’identité, sans modifier maintenant l’API publique.

Une passe de massing plus pauvre n’est pas le levier démontré : **zéro sommet/face de roof_mesh** sur les7354 membres V2 (7352 V1). `plans.rs:1513` réserve déjà un mesh vide ; `realize_plan:3648` réalise volumes/toits puis intérieurs à la demande. `engine.rs:1104–1124/1310` prépare déjà le squelette/support/portail sans subdivision des pièces ni tessellation du toit. Les murs/cadres pré-entrée déterminent des droits physiques : on ne peut pas les différer comme décor. Les caches locaux `PreparedPlan:162–300` sont déjà paresseux/OnceCell par résolu et les alternatives réutilisent leur graphe. Un sondage des archives locales, retirant config/diagnostics/contexte/entrée, trouve7353 signatures différentes sur7354 membres ; ce sondage **n’est pas une clé de cache valide** et ne mesure pas les candidats intermédiaires. Il ne justifie pas un gros cache inter-villes. Une vraie clé intrinsèque devrait conserver tous paramètres/draws/dimensions/topologie/version et le contexte/mode de portail effectivement lus ; jamais le seed seul, jamais des gardes d’occupation ou de terrain mémorisées d’un autre site.

La littérature fournit un découpage utile, pas une nouvelle autorité : [Müller et al., CGA shape,2006](https://dl.acm.org/doi/10.1145/1141911.1141931) distingue composition volumétrique, détails et règles de contexte ; garder ici ailes orthogonales/minima/cours et leurs opérateurs réels. [CityEngine, export/instancing](https://doc.arcgis.com/en/cityengine/latest/help/help-export-models-overview.htm) réutilise les assets insérés et sépare géométrie, instances et transformations ; cela convient aux éléments répétés du rendu, sans certifier des maisons différentes par redimensionnement visuel. [OGC3D Tiles1.1,§6.7/7.2](https://docs.ogc.org/cs/22-025r4/22-025r4.html) organise HLOD/erreur visuelle/instancing pour diffuser le contenu : le LOD ne résout pas les coûts des contraintes natives. L’archive native reste fidèle ; utile/habitants logés restent inconnus.

Mesure root proposée : quatre tests causaux0/2 unions, erreurs/quota/entrée invalide inchangées, positif et fallback archive-exacts ; puis les132 lots originaux avec **132/132 archivesV2 bit-exactes obligatoires**, comptes/IDs/prefix/contexte/refus/open/materials/rapports identiques hors seul timer. Toutes sorties sont conservées avant assertion d’équivalence, aucun rejeu/remplacement pour forcer le résultat. Mesurer appels unions, wallAPI et CPUprocessus ; le nouveau contrôle de référence ajoute du coût de preuve séparément chronométré. Comparer les CPU causalement demande une baseline appariée avec le même harness. Aucun build/test/natif/produit exécuté par l’auteur.

# Transport urbain : prochain palier 100k → 1M

Audit de lecture du 22 octobre 2026, après publication progressive des requêtes originales par lots. Aucun benchmark, serveur ou code applicatif modifié. Complète [OPUS_PERF.md](OPUS_PERF.md), sections 1/5/8 ; ne reprend pas le chantier GPU.

**Priorité : `partitionsId` dans une session explicitement partageable, puis source de sites révisionnée et paginée.** Cela supprime le renvoi des parcelles et les objets JSON géants de sites, sans remplacer leurs contraintes natives par des approximations.

## Ce qui est déjà borné, et ce qui ne l’est pas

| Chemin actuel | Constat et source |
|---|---|
| Entrée HTTP native | `MAX_BODY = 128 MiB` limite les **requêtes**, pas les réponses (`rust/crates/local/src/main.rs:18,663`). Opus a mesuré 313 Mo de réponse parcelles à 1M ; leur renvoi à `buildingSites` dépasse ce plafond. L’augmenter déplacerait le problème vers JSON et les copies. |
| Sites natifs | `urban_reply`, ligne 435, redésérialise tous les layouts et partitions, puis renvoie tous les sites. `value()`, ligne 117, clone aussi le `Value` avant conversion typée. Le générateur construit un `Vec<Value>` entier (`core/src/urban/building_sites.rs:194,430`) ; `cadastral`, `buildable` et `roof_domain` répètent le lot (434). Le corpus du smoke contient **60 957 253 octets pour 10 960 sites** : mesure de taille d’un replay, pas un nouveau chronométrage natif. |
| Plans actuels | `architectureBatch.ts:26,27,104` découpe déjà en **64 requêtes maximum / 24 MiB d’entrée**, réduit le lot si nécessaire ; `urbanArchitecture.ts:84` refuse une réponse dépassant 64 MiB après lecture. Archivage puis publication avec ACK par lot. L’extrapolation « JSON plans unique de 650 Mo » d’Opus **ne décrit donc plus le chemin City courant**. |
| Worker → interface | `urbanSceneWorker.ts:62,82` publie maintenant les requêtes originales avec chaque lot et un message final de compteurs, sans scène ni requêtes complètes. `urbanScene.ts:44–63` valide et accumule ces lots. **La dernière copie monolithique des 61 Mo est supprimée structurellement**, sans nouveau timing mesuré. Les sites arrivent encore du serveur en une seule réponse. Le mode silhouette reste monolithique. |
| Mémoire résidente | `architectureBatch.ts:81,123` conserve toute la scène dans le worker, tandis que le client en accumule une autre ; les requêtes originales restent également conservées. `compactPlanArchive.ts:9–13,162` borne chaque archive à 64 plans et le cache décodé à 2 archives / 8 MiB : ce plafond **n’inclut pas** toutes les chaînes gzip/base64 et la géométrie visible, qui restent proportionnelles à la ville. |

## Changement minimal proposé

1. **Conserver les partitions avec les layouts.** `Session` ne retient aujourd’hui que les layouts (`local/src/main.rs:24–30` ; route parcels : 416–434). Ajouter une révision de partitions et renvoyer un handle opaque `{session, terrainRevision, layoutsRevision, partitionsRevision}`. Accepter ce handle et les IDs du périmètre sélectionné dans `buildingSites`, sans tableaux de géométrie. Le chemin explicite reste disponible pour les petits appels et les modifications non retenues. Invalider les références lors d’un changement de terrain/quartiers/parcelles/programme ; une référence périmée doit échouer clairement.

   **Dépendance essentielle :** `nativeRasterClient()` enferme un UUID privé par instance (`nativeEngine.ts:39–47`). `urbanWorker` et `urbanSceneWorker` créent chacun leur moteur : un simple `partitionsId` numérique ne permet pas de retrouver les données de l’autre session. Exposer un handle natif transmissible, avec propriétaire de session/release défini ; éviter de réuploader un raster dans la session partagée pour consulter ses sites. Les 8 sessions natives sont évincées selon leur usage, sans budget mémoire (`local/src/main.rs:19,37–62`) : prévoir l’erreur de référence expirée et une régénération contrôlée.

2. **Préparer une source, puis construire seulement une page de sites.** Contrat possible : `buildingSitesBegin(handle, selectionIds, seed, culture) → {sourceId, total}`, puis `buildingSitesPage(sourceId, offset, limit≤64, maxBytes) → {requests, next, total}`. Conserver une liste d’allocations éligibles et les index parcelles/adjacences/cultures préparés une fois ; produire le patch terrain et les contraintes uniquement pour la page demandée. Ne pas appeler l’actuel `requests()` sur toute la ville pour découper son résultat à chaque page. Ordre, IDs, graines, nombres et contraintes doivent rester identiques au chemin complet. La source inclut la sélection et la culture ; ce n’est pas seulement une référence aux partitions.

3. **Consommer les pages dans un seul placement continu.** Étendre l’adaptateur à une source paginée/`AsyncIterable`, tout en conservant son index d’occupation, ses IDs déjà vus et sa progression globale entre pages (`architectureBatch.ts:49–80`). Appeler séparément `planUrbanBuildings` pour chaque page perdrait les voisins précédents : incorrect. Garder l’ACK et le protocole de lots existants. Ensuite, un mode de résultat « flux seulement » peut libérer les plans/archives du worker après ACK, en ne gardant que l’occupation nécessaire et les compteurs ; conserver le comportement actuel par défaut pour les autres appelants.

4. **Édition : retrouver le site original par ID.** Remplacer à terme le grand `sceneRequests` de l’interface (`terrainUrban.ts:108,388,955`) par `getPlacementRequests(sourceId, ids)` et un petit cache. Le serveur renvoie les requêtes exactes de cette révision ; les overrides sont appliqués à ces seules requêtes avant `editArchitectureScene`. Une référence native n’est pas un format d’export portable : après restauration sans source vivante, réhydrater explicitement ou régénérer, sans déduire un site depuis son toit. Le comportement actuel demande déjà une régénération pour éditer une scène restaurée sans sites.

## Portée et ordre d’intégration

La pagination conserve le volume total des sites échangés, mais supprime le JSON de 61 Mo d’un seul tenant et les pics associés. Supprimer aussi cet aller-retour exigerait ensuite un endpoint natif « plans depuis source de sites » ; ce n’est pas nécessaire au premier correctif. **La réponse parcelles de 313 Mo reste un problème en amont** : partitions retenues + buffers d’affichage transférables/projections légères relèvent du chantier urbain/GPU d’Opus. Garder les coordonnées et contraintes autoritatives exactes ; le f32 d’affichage ne remplace pas les f64 du placement.

Propriété : Codex pour session HTTP, bridge maisons et protocole de scène ; accord Opus pour `core/urban/building_sites.rs`, contrat urbain et branchement `terrainUrban.ts` ; ne pas modifier ses buffers GPU. Activer le nouveau chemin par capacité native, avec chemin WASM existant conservé. Validation ciblée suffisante : égalité des sites complets/paginés (y compris la convention actuelle de conversion décimale), voisins franchissant une page, référence périmée, édition d’un ID sans charger la ville. Aucun nouveau banc géant requis pour valider le contrat.

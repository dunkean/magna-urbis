# Cooperative camera refresh cancellation

This change cancels CPU preparation only when its revision and world ID were
already displayed when that job started. Accepting a newer revision can request
cancellation of that camera refresh. A newly accepted world that has not been
displayed remains non-cancellable, even when further previews arrive.

The mutex-protected request becomes an observed cancellation only at a
checkpoint. Height and prefilter reconstruction check every eight rows;
ScenePrepare also checks between sub-phases. No source samples, candidate IDs,
arithmetic, interpolation, grid dimensions or source resolution change.

A completed obsolete camera refresh is skipped before water baking (and checked
again after its asynchronous bake). Such completion races increment
`skippedCameraRefresh`, separately from `cancelledSuperseded` recorded at an
actual checkpoint. Both paths immediately schedule the latest accepted revision.
Existing physical-lineage rejection remains in place. Full accepted-world
preparations and real displayed-source evidence keep their previous semantics.

Godot 4.7.2 headless CPU test, 2026-10-24: **32 checks passed**, including a
concurrent cancellation at the fifth height-row checkpoint, anti-starvation,
completion racing cancellation, distinct counters, immutable source samples and
six byte-identical non-cancelled images (height, control, material IDs, state,
bedrock and mean response). Spacing, import origin, context grid and height range
also match the frozen baseline. This is authored-fixture CPU evidence, not a
fresh-source, GPU or navigation performance result.

The test does not prove a particular navigation latency. A fresh campaign is
still required after integration with the independent stdout and probe fixes.

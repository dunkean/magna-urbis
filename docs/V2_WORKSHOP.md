# Magna Urbis V2 Workshop

V2 is a standalone entry point, `web/src/ui/v2.html`. It reuses the existing cores with a new bilingual interface: a central map, dark glass, brass, painted iconography and progressive settings.

English is the default language of the application and of the atlas. The **English / Français** selector switches the application language in place, without regenerating the map, moving the view or losing settings. The choice is remembered and shared with the atlas; `?lang=en` or `?lang=fr` selects it explicitly.
The atlas provides two complete pages, `scientific/index.html` in English and `scientific/fr.html` in French, both readable offline without JavaScript.

## Run, build and distribute

From `web/`:

```sh
npm ci
npm run prepare:v2       # First Rust/WASM preparation; requires wasm-pack
npm run dev:v2           # http://127.0.0.1:5174/v2.html
npm run dev:v2:local     # Native Rust and optional Python services
npm run build:v2         # Distribution in web/dist-v2
npm run app:v2:dev
npm run app:v2:build
```

Prerequisites, optional models, Python variables and installable packages are documented in [the distribution guide](../rust/desktop-v2/README.md).
The contents of `web/dist-v2` are served from a GitHub Pages subfolder, for example `/magna-urbis/v2/`. Assets, workers and scientific links are relative. Building this distribution does not publish any remote file.

The Windows MSI and NSIS installers are produced in `rust/desktop-v2/target/release/bundle/`. The Rust engine is embedded. Python, CUDA and local weights remain external, configurable dependencies.
Browser models are copied from `rust/pkg/neural-web` when they have been prepared; their absence must not be mistaken for a model that is already loaded.

## The stage chain (interface)

The left panel shows the entire generation chain in five painted families: **Relief → Water & cover → Settlements → City → Display**. The rows come from a single source, `web/src/v2/stageRegistry.ts`, which uses exactly the identifiers from [`stage-registry-contract.md`](stage-registry-contract.md).
Each stage row offers, on a single line:

- the **node** on the brass thread: a click enables or disables the stage (diamond = mandatory stage; dotted = no engine switch, reason in the tooltip);
- **▶**: regenerates from this stage (relief and water: the topography; sites, hierarchy: the settlements; roads: the roads alone; city: the corresponding Rust stop for the chosen place; display: the rendering);
- the **duration** of the last run (green = up to date, amber = settings changed since; empty = computed inside a neighbouring stage, with no invented timing);
- **?**: the `#stage-<id>` section of the scientific atlas, in the application language;
- the chevron: all options. The main settings remain accessible on the collapsed row.

The rows are conditional: procedural, neural and heightmap modes do not have the same stages. Importing a heightmap or choosing a map from the **test library** (six 16-bit PNGs generated by our engine, `web/src/v2/assets/heightmaps/`, rebuilt by `node web/scripts/v2_heightmap_library.mjs`) is an alternative for the **relief source**; the **Heightmap adjustment** stage controls vertical scale, datum, cropping and width without losing the source.

No control has been recreated: the existing forms (terrain, region, City Bench urban recipes, appearance) have been moved into the stage that runs them; a test (`web/tests/v2StageRegistry.test.ts`) verifies that each control belongs to exactly one stage. The addresses of models and services are in **Settings**, together with the state of the engines: WASM (single thread, threads, pool, depending on cross-origin isolation), WebGPU, **Native Rust**, **Neural Python** and the GPU/CPU rendering path. An unavailable choice remains visible, disabled, with its reason. For cities, generation is on the left and the **place selection** is on the right (list and local settings). Icons are generated by ImageGen (`web/src/v2/assets/icons/PROVENANCE.md`).
## The workflow

**Create my region** generates only the relief, water and natural cover.
Settlements and cities come afterwards:

1. **Topography**: relief, drainage, rivers, lakes, shorelines and natural cover.
   New regions start at 6 km per side, with a procedural scale of 10 km and vector hydrology. Width and scale are independent.
   Automatic extent remains optional; the neural engine produces a 40 km source.
2. **Settlements — place and connect**: site selection, urban reserves, hierarchy of places and regional roads. No buildings are created at this stage.
3. **Build settlements**: all settlements or a single selected settlement.

The first opening stays empty: first set the free width, the combinable coasts (eight directions), then the engine and the source. Rust is offered by default; the installable edition uses its Native Rust service directly.
Its actual range is 500 m to 100 km; the classic TypeScript engine keeps its range of 600 m to 40 km. The panels detail the relief families, climate, neural models, diffusion parameters, erosion, fractal refinement, hydrology and forest.
Zones can be painted before any generation; the editor also accepts and exports 16-bit PNG heightmaps and zone instructions in JSON.

Rust settlements offer automatic, class-based and explicit-list compositions, with positions, site preferences and ranking criteria. Roads have their own profile, surface and travel costs. **Recalculate roads without moving settlements** reuses the selected sites; a change to their recipe requires redoing the settlement placement.
Rust fields and hydrological networks are kept with the relief, without any additional TypeScript drainage.

Existing terrain keeps its extent when population or the number of settlements is then adjusted. A change to relief, world seed or hydrographic parameters requires recreating the topography. Changes that move sites require recalculating settlements and roads.

The Rust urban engine offers four real stops:

| Stop | Visible outputs | Settings |
| --- | --- | --- |
| Plan | Extent, phases, districts, streets, blocks | Grid, density, growth, defences, relief, functions |
| Parcels | Cadastral division and access | Operators, zones, shapes and lot edits |
| Programme | Assignments, needs and capacities | Functions, resources, context and settlement states |
| Houses | Buildable areas and architectural plans | Recipes, materials, storeys, wealth, variation and constraints |

The classic TypeScript engine generates its complete urban plan in a single operation. Its internal steps are not presented as Rust stops.
## From global settings down to the house

The main panel sets the shared values. A location's inspector lets you override these values locally. The structured forms mirror the `LayoutConfig`, `ParcelConfig` contracts, the morphological catalogues, `PlacementBatchSettings` and `HouseConfig`, with inheritance and reset-to-default per field. JSON recipes remain accessible for inspection and exchange.

Enable **Inspect**, choose the level, then click the map:

- A **Rust district** accepts culture, grid, density, wealth, shape, role, deletion or a local seed (`salt`).
- A **Rust parcel** accepts function, households, shape, merge/garden or a local seed.
- A **house** accepts edits to its representation and footprint. A Rust house also exposes its real `HouseConfig` configuration and a native regeneration, linked to the identifier of its request.

Individual house configurations use the key `settlementKey/nativeRequestId` to avoid collisions between towns. The constraints of a recipe remain active: requesting four storeys from a recipe that allows three produces an explicit refusal. The engine report shows the reasons and lets you correct the configuration and try again.

The inspection also offers direct actions: **New variation**, **Delete**, **Edit outline**, and the choice of role, culture and grid of a district. The outline is edited on the map: drag a vertex, click an edge to add one, then **Validate**. Deleted zones can be restored from the location's inspector. A native house has an individual draw and the architectural catalogue.

**Map → Names and labels**, also accessible at the top of the map, lets you search existing names, name districts, parcels and houses, or create a free label. The text, colour, size, bold, italic and coordinates can be edited. **Select on map** chooses an element; **Place on map** sets its new position. Labels are kept in the project and the recipe, and carry over into visual exports.

**Region → Delete a river** selects a watercourse and previews all the tributaries and branches that will disappear with it. The relief is preserved. Under **Settlements → Regional roads**, the tools let you draw, move and delete a road, or edit its points, category and width. These direct adjustments are kept in the **full project**; a new generation of the network replaces them. Towns already built may request a reconstruction to adapt their access and banks.

The render selector offers the twenty existing styles: nine V1 palettes, Render Neural Earth, Render3D Multiscale and Brush, satellite Render v2 and its four material views, Fantasy ink and watercolour, and DEM altitude. The render settings add season, lighting, layers, painted natural textures and canopy.

The Terrain / City Bench engine reuses the native data kept: five urban views, five city palettes, cartographic and geometric silhouettes or roofs, usage/height/access diagnostics, materials and shadows per volume. The classic V1 map remains selectable. No change of appearance recalculates the relief, the placements or the houses.

The **3D** button reuses the terrain and architectural scenes of City Bench, with terrain materials, season, lighting, canopy, physical water, textures, colours, exaggeration and PNG capture. On software WebGL, the same material is computed as a texture then draped over the geometry, with an explicit indication. The cast shadows of houses are those of the native 2D render; the shared 3D engine does not provide new building shadow maps.

The inventories of correspondence with the benches are in [the terrain matrix](design/v2-terrain-controls.md) and [the urban matrix](archive/studies/V2_URBAN_PARITY.md). The optimisation review (historical validation, archived locally) details the removed copies, the caches, the rendering, the before/after measurements and the identity checks of the results.

The **Edit roads** and **Draw a road** commands are accessible in the **Editor** tab. In edit mode, a click on the line selects the whole road, or the control point under the click. Double-clicking a point selects the line; double-clicking the line adds a point that is immediately selected, without modifying the existing route. A 500 ms press on a line already selected selects the segment between two control points. Dragging the line moves the road, dragging a point recalculates its path. Connections to towns and to other roads remain fixed during a global move; moving a crossroads recalculates its incident branches together. Connections to towns remain fixed.

The **Add a waypoint** button also lets you choose a location on the line. Moving a segment moves its two points and keeps the incident connections; **Del** removes the selection (point, segment or line). Access roads to farms and farm tracks can be selected and edited like other roads. Around the selected point, **minus** removes the passage constraint and recalculates the path between its neighbours. The **scissors** create a visible break: one click creates two lines and two independent endpoints, separated by a small physical gap that stays stable when the zoom changes. The controls are distinct from the vertices of the calculated path, remain stable when zooming, and are kept with the full project.

Automatic controls do not replicate every calculated bend: an existing road starts with its two endpoints and a central handle. On release, the engine searches the path again on the relief; the resulting bends do not become passage constraints. The preview during movement also uses this routing.

The **Other route** die is available during creation (after two points) and on a selected road. It keeps the points and connections, but explores another seed and another slope-cost trade-off, without relaxing the maximum slope or the crossing rules. If the search finds the same practicable passage, the editor indicates it.

**Draw a road** places a sequence of waypoints: the Rust engine computes the successive links using the regional settings for slope, crossing and culture, for the chosen road category. The preview follows the cursor. **Escape**, **Enter** or **Finish road** validates the draft; **Cancel** abandons it. A first click off the map creates an entry on the nearest edge. A click off the map after the start adds an entry and ends the road. A through road can therefore have two entries.

Regional entries are diamonds constrained to the edge. Deleting them asks for confirmation and removes their exclusive branch while keeping the shared sections. The **Regional roads** component updates its results and the requested count for the category concerned. A cut link is flagged as unconnected. **Undo/Redo** restores both the map and these counts (Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z or Ctrl+Y).
Recalculations run in a worker. A failure keeps the previous valid map; **Escape** during a calculation interrupts it. Changes remain saved in the project, but a regional regeneration replaces them.
The use of existing roads as a sharing network during path search is not exposed by the current API; their connections are kept.

After a change, forest clearings follow the new route, including outside cultivated areas; the abandoned clearing disappears.
The large **Finish editing** button, placed above the minimap, stays visible with the number of actions and the result of the last operation, until validation or **Cancel road editing**. Moves, additions and deletions remain visible during adjustments; settlements wait for validation. **Escape** finishes a route without validating the whole session.

On validation, the changes are compared with the initial state. A single dialog groups the hamlets, villages and larger places actually affected, and offers **Adapt only the access roads** or **Rebuild affected blocks** (parcels and buildings). Modified streets keep priority and are saved; a later regeneration reapplies them. Only the blocks crossed by the old or new route are re-subdivided; the other blocks, quarters and buildings are kept. **Continue editing roads** returns to adjustments without applying this choice. Isolated farms and buildings concerned are updated directly on validation. A change far from a settlement does not trigger any question. **Cancel** restores the map and the regional entries from the start of the session; **Ctrl+Z** undoes each action, deletion included, even after the tool has been closed. Undoing the validation reopens the draft; the previous actions can then still be undone individually.

Internal streets and urban access roads can be selected in the same editor, including small roads that extend beyond the town. The panel shows their settlement. Moving a junction keeps the incident streets; deleting or cutting a street allows manual cleanup. A route created entirely within a settlement becomes a street of that settlement.

The population distribution no longer caps villages at 999 inhabitants. The chosen headcounts are kept; the displayed demographic designation may change with the number of inhabitants.

The **Quarter**, **Block** and **Parcel** tools apply the same gestures to the outer outlines: click to select, double-click on an edge to add a point, double-click on a point to select the entire outline, long press to select a segment. Moving this segment moves its two vertices. **Delete** removes the selection; removing a point retightens the outline.
The scissors on a point ask for a second point on the outer edge and create two closed surfaces. A cut crossing an inner courtyard is refused.
Urban dependencies are recalculated on release; streets, relief, countryside and other settlements are kept. The admissible limits remain those of the engine (neighbours, streets and reserved surfaces).
**Ctrl+Z** restores the outline and its dependencies, including after **Finish editing**. The project saves the control points and splits.

The settlement list also lists **Isolated farms** derived from land use, with their category (farm or outlying agricultural holding), the number of households, the nearby settlement and their connection to the network. These households are already included in the population of the settlements: displaying them adds no inhabitants. Their access roads are computed on the ground, go around obstacles and may join an existing agricultural access. A farm with no passable route is marked **no path**. After an edit of the network, this indicator is updated; the access roads themselves are recalculated at the next land use generation.

The **Topographic** render is a simplified working view: plain background, contour lines, boundaries and field strips, rivers, roads and towns. It keeps the land use data in the project but displays neither its flat fills nor the vegetation.

## Engines, activity and hardware

Procedural CPU generation works in both editions. The Rust relief can use WASM/CPU, WebGPU or the native service. The existing neural engines use WebGPU in the browser or Python/CUDA locally; they currently offer no CPU inference.

**Engines & activity** shows the detected capabilities and the log of operations. A WebGPU detection is not proof that the GPU is being used: the log and the world statistics record the effective backend.
A forced GPU must not silently fall back to the CPU. The automatic choice may rerun a procedural relief on the CPU, flagging this fallback.

The activity bar covers model loading, computation, cache and map drawing. The generation and rendering workers are separate. Rendering uses the existing levels of detail and tile caches.
## Save, compose and export

**Full project** keeps the exact numerical grids, the base map,
the settings, the native snapshots and the edits. The typed FP32/Int32 arrays
and infinite costs are rebuilt on re-import.

**Seeds + settings + edits** keeps the recipe without the map.
Reproduction requires the same versions of engines, catalogues, models
and backends. Numerical differences between GPU devices remain possible;
the full project keeps the exact fields of the result.

**Seed only** contains only `format`, `version` and `seed`. It starts
from default values: it does not claim to contain your custom settings.

Imports let you choose:

- The full project.
- The exact territory of a project, with the current city recipe.
- The city recipe of a project, on the current territory.

Compositions remove the old urban geometries before rebuilding them in their
new context. They keep the elevations and hydrology of the selected territory
and feed its persistent cache.
If the file contains a settings draft that differs from the saved map, the exact
elevations of the result become a portable FP32 input, rather than rerunning a
different model.

**SVG and PNG** exports independently choose style, elements and crop area.
Creating them does not rerun the generation. The SVG export of Terrain / City Bench
renders embeds the composed image; the classic V1 export keeps its vector objects.
Streets and buildings remain exportable independently, with transparency and
respect for the selected layers.
The **heightmap PNG** export is quantised to 256 levels and accompanied by a
min/max JSON; the full project keeps the FP32 values. Image import reads
greyscale levels, crops to a square and lets you adjust elevation and sea level.

## Cache and invalidation

Terrain and hydrology have a versioned key, independent of the style and the
culture of the cities. Imported pixels or elevations are part of this
key. An LRU in-memory cache holds two terrains; IndexedDB holds the three
most recent terrains. If storage is unavailable, the in-memory cache remains usable.

Rust urban snapshots separately keep the keys for the plan, the cadastre, the
programme, the buildable domains and the houses. An individual house edit reuses
its upstream stages and preserves the neighbouring occupations. The native log
makes it possible to audit the number of recomputed requests.

## Reproducible checks

```sh
npm run typecheck
npm run test:v2
npm run test:v2:browser
npm run test:v2:urban
npm run test:v2:urban-ui
npm run test:v2:platform
npm run test:v2:static
npm run test:v2:locales
node scripts/v2_compose_browser_check.mjs
```

Browser checks require an active V2 server; `MAGNA_V2_URL`
lets you choose its address. The static check serves the built distribution
under `/magna-urbis/v2/`. The real models can be tested with
`MAGNA_TEST_NEURAL=all`; this check may load weights and use the GPU.

The scripts write their captures, results and recipes to `web/out/`:
`v2-browser`, `v2-compose-browser`, `v2-rust-urban`, `v2-native-urban`,
`v2-platform-check.json`, `v2-static-check.json` and
`v2-desktop-startup.json`. Each proof covers its own scenario and hardware,
without claiming to cover all cultures and all possible sizes.

The [illustrated scientific documentation](scientific/index.html) explains the
methods, their sources, their assumptions and their limitations. The [V2 iconography
and its ImageGen prompt](../web/src/v2/ASSETS.md) are also documented.
